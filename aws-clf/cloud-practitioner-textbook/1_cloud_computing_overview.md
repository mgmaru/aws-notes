# 第1章　クラウドコンピューティングの概要

## 備考

## メモ
### 2026-9-18
1. **クライアント・サーバモデル**
2. **オンプレミス**：必要なハードウェアやネットワーク機器、ソフトウェアなどを自前で調達し、管理・運営する。
- 課題①：**キャパシティ設計の難しさ**
  - **キャパシティ**：必要なサーバの性能やストレージの容量（サービスの許容量）
  - キャパシティを見積もる必要がある。
- 課題②：**機材調達の問題**
  - 調達する機材は発注してもすぐに届くとは限らない。
  - 故障などが発生した際に、機器の取り替えを行わなければならないが、すぐに交換できない。
3. **クラウドコンピューティング**
  - **クラウドサービスプロバイダー**：ITリソース（CPU、ネットワーク環境、ストレージ、ソフトウェアなど）を提供する。
    - Amazon Web Services (AWS）/ Microsoft Azure / Google Cloud / Alibaba Cloud / IBM Cloud / Oracle Cloud Infrastructure (OCI) / さくらのクラウド など
  - 利用者は、自分たちが必要なものだけを必要な分だけ使用する。
  - 利用者はサービスがどのように構築されているかを考える必要がない。
- 特徴：
  1. **他社所有**：クラウドサービスプロバイダーが保有するITリソースを使用する。
    - オンプレミスが自家用車なら、クラウドピューティングはレンタカー
  2. **従量課金**：
    - 利用したITリソースに対して課金される。利用しない分に対してコストがかからない。
  3. **インターネット越しの利用**
    - クラウドコンピューティングは、サーバ、ストレージ、ネットワークなどのインフラをインターネット越しに利用する。
    - インターネットを使用できる環境であれば、どこでも利用できる。
  4. **オンデマンド・セルフサービス**：クラウドコンピューティングは、利用者が必要とする機材を必要なときに、画面上で操作するだけで入手できる。
    - オンプレミスの機材調達は、見積もりから発注、納品まで多くの人と時間を要する。
    - 納車まで時間がかかる。
    - 必要なときに利用できる -> レンタカーみたいなもの
4. Amazon Web Services（AWS）の誕生
- Amazon.comにおけるITシステムのさまざまな課題を解決するために誕生したサービス。
- 1995年オンラインブックストアとして誕生。
- **ソフトウェア面の改善**：
  - 当時のAmazon.com：アプリケーションを計画的に構築していくと言うより、必要なサービスをどんどん開発していくスタイルだった。
    - 各サービスが絡み合う複雑な状態になってしまった。
  - **マイクロサービス・アーキテクチャへ移行**
    - マイクロサービスアーキテクチャ：機能ごとにコンポーネントを分離し、API（入出力の仕様）に基づいて連携するように構成されたシステム。
      - **ユーザインターフェースからAPIを通じてサービスに接続**する。
      - **サービスごとにデータアクセス、データストアが分割**されている。
  - モノリシック（モノリス）：プログラム、機能が一体化している。
    - ビジネスロジックに機能がまとまっており、データアクセスとデータストアを共通で利用。

### 2026-9-23
- ハードウェア面の改善：
  - Amazon.comでは、仮想化技術を使用してサーバーやネットワーク、ストレージを置き換えてきた。
    - **仮想化された環境をAPIによって置き換えられるようにした。**
  - 仮想化技術：ITリソース（サーバー、ストレージ、ネットワークなど）をソフトウェアによって論理的に実現する技術。
    - 仮想サーバ：物理的なサーバの上に複数の仮想化されたサーバを構築する。
    - 仮想ネットワーク：物理的なネットワーク装置やケーブルの接続状況とは別に、論理的にネットワークを分離、構築する。
    - 仮想ストレージ：複数のストレージ装置で構成される仮想ストレージの中から必要な容量を取り出して、個別のストレージデバイスであるかのように見せる。
- 2006年からAmazon Web Servicesを開始。
5. AWSで提供される主なサービス
- コンピューティングサービス：
  1. **Amazon Elastic Compute Cloud（Amazon EC2）**：AWSクラウド上で稼働する仮想マシンを提供する。
    - LinuxやWindowsなど好きなOSを選択できる。
    - **Amazon EC2 Auto scaling**：仮想マシンの台数を負荷に応じて自動的に増減する。
    - **AWS Lambda**：サーバーの構築や管理運用を気にせずアプリケーションを実行する。
- ネットワークサービス：
  1. **Amazon Virtual Private Cloud（Amazon VPC）**：AWSクラウド上に仮想プライベートネットワークを構築する。
  2. **Amazon CloudFront**：Webコンテンツのキャッシュサーバー
- ストレージサービス：
  1. **Amazon Elastic Block Store（Amazon EBS）**：仮想マシンのボリューム
  2. **Amazon Simple Storage Service（Amazon S3）**：各種データの保存場所
  3. **Amazon Elastic File System（Amazon EFS）**：ファイル共有
- データベースサービス：
  1. **Amazon Relational Database Service（Amazon RDS）**：SQLデータベース
    - **Amazon Aurora**：AWSがクラウド向けにストレージやレプリケーションなどの仕組みを独自設計している。
      - レプリケーション：同じデータを複数の場所にコピーして保持する仕組み。
        - バックアップとは違い、リアルタイムで別の場所に複製する仕組み。
  2. **Amazon DynamoDB**：NoSQLデータベース
- その他サービス：
  1. **Amazon SageMaker**：機械学習モデルの構築・トレーニングを行う。
  2. **Amazon Athena**：データ分析を行う。
  3. **Amazon Simple Notification Service（Amazon SNS）**：メッセージを通知する。
  4. **Amazon Connect**：コールセンターを構築する。
6. クラウドコンピューティングの概念：5つの特徴
- **On-demand self-service（オンデマンド・セルフサービス）**：利用者が必要なときに自分自身でITリソースの調達をおこなうことができる。
  - 不要になったITリソースの削除もできる。
- **Broad network access（幅広いネットワークアクセス）**：PC、スマートフォンなど様々なデバイスからクラウド上のITリソースへのアクセスが可能。
- **Resource pooling（リソースの共有）**：利用者は自分が利用するITリソースの所在地や物理的な構成をほとんど意識する必要がない。
- **Rapid elasticity（迅速な拡張性）**：必要に応じてサーバーの性能や台数を、利用者が任意のタイミングで拡張したり縮小したりできる。
- Measured service（計測可能なサービス）：クラウドコンピューティングでは、利用者が利用しているITサービスを常に監視・計測し、利用者はいつでもそのレポートを受け取ることができる。
  - 現在の利用料金も含まれる。
7. ３つのサービスモデル
- IaaS（Infrastructure as a Service）：物理的なハードウェアやネットワーク回線などの基礎的なインフラストラクチャが利用者に提供される。
  - 利用者は提供された環境に任意のOSやアプリケーションを導入して利用することができる。
  - メリット：自由度が高い。利用者が使い慣れた環境を利用できる。
  - デメリット：**OSより上のレイヤーを自分たちで管理・運用**する必要がある。
  - 該当サービス：Amazon EC2
- PaaS（Platform as a Service）：サーバーやネットワークが利用者に提供される。
  - メリット：Webサーバーやアプリケーションサーバーで動かすことができ、サーバーの構築や運用が不要。
  - デメリット：サーバーのソフトウェアの種類やバージョンが合わないことがある。
  - 該当サービス：Amazon RDS
- SaaS（Software as a Service）：アプリケーションまで全てのレイヤーが利用者に提供される。
  - メリット：利用者はアプリケーションを新規に構築することなく、すぐに利用することができる。
  - デメリット：　特定の要件に応じてアプリケーションをカスタマイズできないことが多い。
  - 該当サービス：Amazon Workspaces
8. 4つの展開モデル
- **パブリッククラウド**：クラウドサービスプロバイダーが提供するサービスを広く一般の利用者が自由に利用することができる。
  - **全てのITリソースはクラウドサービスプロバイダーの管理・運用する敷地内に存在**する。
  - 複数の会社がパブリッククラウドを使用する。
- **プライベートクラウド**：クラウドが提供するITリソースを、単一の組織や団体が専用利用します。
  - **組織や第三者あるいはその両方によって所有、管理、運用され、組織の敷地内に存在**している。
  - オンプレとは違い、利用者から見ると、自己所有せず利用している形になる。
- **コミュニティクラウド**：クラウドが提供するITリソースを、地方自治体や研究機関など、**共通の目的をもった複数の組織や団体が専用利用**する。
  - 提供されるサービスやインフラは**共同体内の単一組織か、第三者、両方によって所有、管理、運用**される。
- **ハイブリッドクラウド**：複数の形態を組み合わせて利用する。
  - 災害対策や特定のベンダーに依存しないインフラを構築する場合に利用される。

### 疑問
1. 「論理的に実現する」とはどういうことか？
- 回答：
  - 物理：実際に手で触れる機械のこと
  - 論理：ソフトウェアで決めた「区切り方」や「見せ方」
  - 例：PCのディスクを「Cドライブ」と「Dドライブ」に分ける。
    - SSDは物理的には1台だが、OSから見ると2台に見える。
  - ソフトウェアで作ったものは、APIで作成・変更、削除できる。
    - 物理サーバを増やす場合：発注、納品、設置、配線で数週間かかる。
    - 仮想サーバを増やす場合：APIを呼ぶか、画面のボタンを押すだけで数分で済む。
2. 「論理的にネットワークを分離、構築する」とはどういうことか？
- 回答：
  - 物理的な分離：経理部と開発部のネットワークを分けるには、スイッチやケーブルを分ける必要がある。物理的に繋がない。
  - 論理的な分離：スイッチやケーブルは共用のまま、設定（VLANなど）で「A部署の通信はB部署に届かない」ようにする。
    - 設定で見えない壁を作るイメージ。
3. AWS Lambdaとはどのようなサービスなのか？サーバレスというのがこれ？
- 回答：
  - 概要：関数を置いておくと、呼ばれたときだけ実行してくれる。
    - OSのパッチ当てや管理：AWSがやる
    - 動いている時間：イベントが来た時だけ
    - 課金：実行回数＋実行時間
    - アクセスが増えた時：自動で並列実行される
  - サーバーレス：サーバーがないことではない。
    - 正しくは、**利用者がサーバを意識・管理しなくて良い。**
  - 苦手なこと：
    - 1回の実行は最大15分。長時間のバッチ処理には向かない
    - しばらく呼ばれないと、次の実行の立ち上がりが遅い（コールドスタート）
4. Amazon VPCとは、VPNとは違うのか？また、VPSとは何？
- 回答：
  - **VPC（Virtual Private Cloud）：AWS上に作る自分専用の仮想ネットワーク**
    - イメージ：自分専用の区画
  - **VPN（Virtual Private Network）：インターネット上に暗号化したトンネルを作り、離れた場所を安全に繋ぐ技術**
    - イメージ：区画へ通じる専用の線路
  - **VPS（Virtual Private Server）：物理サーバーを仮想化で分割して貸し出すレンタルサーバ**
    - イメージ：借りる部屋
5. 「Elastic」ってどういう意味？
- 「弾力性のある、伸縮自在な」という意味。
- サービス例：
  - EC2（Elastic Compute Cloud）：サーバの台数やサイズを伸縮できる。
  - EBS（Elastic Block Store）：ボリュームの容量を後から拡張できる。
  - EFS（Elastic File System）：保存したファイルの量に合わせて容量が自動で伸び縮みする。
  - ELB（Elastic Load Balancing）：トラフィックに応じてロードバランサー自体がスケールする。
- 用語の注意：
  - **スケーラビリティ**：**負荷の増加**に対応して拡張できる能力*
  - **弾力性（Elasticity）**：**需要**に合わせて自動で拡張・縮小できること
6. プライベートクラウドとオンプレミスの違いは何か？どこのレイヤーから分離されているのか？
- 時々、プライベートクラウドのサービスでGPU提供サービスがあるが、このサービスがどのようなものなのかを調査する。
- 回答：
  - **オンプレとプライベートクラウドの違い：リソースを手に入れる方法**
  - **プライベートクラウドとパブリッククラウドの違い：専有か共有か**
- GPU提供サービスについて：
  - 事業者のデータセンターにあるGPUサーバを1社に専有で貸し出す。
7. ハイブリッドクラウドが良さそうに見えるが設計が難しそう。実際にどのように分離するのかを調査する。
- 回答：
  - 設計パターン：
    - **機密性で分ける**
      - オンプレ：個人情報や機密データ
      - クラウド：Webの画面、分析基盤
      - 例：金融機関、病院
    - **移行の途中**
      - オンプレ：既存の古いシステム
      - クラウド：新しいシステム
    - **災害対策（DR）**
      - オンプレ：本番環境
      - クラウド：待機系
      - 本社のデータセンターが被災したらAWSに切り替える
    - **バックアップ**
      - オンプレ：本番データ
      - クラウド：バックアップ（S3）
8. ただし、仮想化技術はあくまで利用者目線では論理的な恩恵を受けることができますが、プロバイダは物理的なものを構築しないといけないんですよね？
- 回答：
  - **物理的な設備がなくなるのではない。リソースを持つ人が利用者からプロバイダに変わるだけ。**
  - **プロバイダもオンプレと同じ「キャパシティ設計」や「機材調達」の課題を抱える。**
  - ただし、利用者も物理サーバが故障することを前提に設計する必要がある。
    - **アベイラビリティゾーン（AZ）**を複数使ってサーバを分散させる設計
9. 「専有」というのは、物理的な専有なのか、ネットワークの専有なのかどっちなのか？
- 回答：
  - サービスによる。
  1. パブリッククラウド（通常のEC2）
    - 建物・電源：共有
    - 物理サーバ：共有（論理的に分離）
    - ネットワーク：共有（VPCで論理的に分離）
  2. EC2 Dedicated Hosts：
    - 建物・電源：共有
    - 物理サーバ：専有
    - ネットワーク：共有（VPCで論理的に分離）
  3. ホステッド型プライベートクラウド
    - 建物・電源：共有
    - 物理サーバ：専有
    - ネットワーク：事業者による
  4. オンプレ型プライベートクラウド
    - 建物・電源：専有
    - 物理サーバ：専有
    - ネットワーク：専有
### 思ったこと
- **一言で「専有」と言っても、何を専有しているのかをしっかり意識することが大切**であると思った。
  - アプリの要件によっては、物理サーバ自体を専有にする必要があるかもしれない。。
