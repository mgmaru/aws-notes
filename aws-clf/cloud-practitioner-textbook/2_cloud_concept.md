## メモ
### 2026-9-24
1. AWSクラウドの利点
- **AWSのコンプライアンスプログラム**
  - 概要：AWSはセキュリティやデータ保護の国際規格・法規制を満たしていることを、第三者の監査機関にチェックしてもらい、認証や照明を取得している取り組み。
  - 目的：**（AWSを使用している）利用者が自分のシステムのコンプライアンスを証明しやすくするため**のもの。
  - 背景：
    - 利用者はAWSのデータセンターに入って、物理セキュリティなどを観察することができない。
    - 何百万もの利用者がAWSを監査しに来るのは現実的でないため。
  - 注意点：
    - **責任共有モデルにより、AWSが認証をとっていても、利用者のシステムが自動的に準拠するわけではない。**
      - AWSの責任：データセンター、ハードウェア、ネットワーク基盤（クラウドのセキュリティ）
      - 利用者の責任：IAM設定、データの暗号化、セキュリティグループ、OSのパッチ適用
    - 例：耐震・防犯の認証を受けたオフィスビルを借りるようなもの。ビルの安全性はオーナーが証明してくれますが、自分の部屋の鍵をかけるのは利用者の役目。
  - **AWS Artifact**：SOCレポートやPCI DSSの準拠証明書などのコンプライアンスレポートをダウンロードしたりできるポータル。
2. **信頼性**
- **信頼性**：ハードウェアやソフトウェアの故障や不具合により、データの消失やシステムの故障が発生しにくい状態。**故障した状態から早期に復旧できる能力**のこと。**壊れにくさ。**
- 世界各地のに複数のデータセンターを保有しているので、データセンターレベルの障害に対しても、他のデータセンターに迅速に復元することが可能。
3. **可用性**
- **可用性**：**稼働している状態を維持できる能力。**
  - **稼働率**として表現される場合がある。
- マネージドサービスとアンマネージドサービス
  - **マネージドサービス**：AWSがサーバーやストレージ、ネットワークなどのITリソースの構築や運用・管理を利用者に代わって実施してくれる。
  - **アンマネージドサービス**：利用者が構築から運用・管理、可用性の確保を行う必要。
    - サービス例：Amazon EC2
    - EC2などの仮想マシンを利用する場合は、**複数のデータセンターを利用して分散配置**することで、データセンターレベルの可用性を考慮する必要がある。
4. **伸縮性**
- **伸縮性**：**必要に応じてリソースを増減できること。英語でElastic**と言う。
  - **急激なリクエストの増加に対して自動的にサーバーを増やしたり、リクエストの現象に合わせてサーバーを自動で減らしていく。**
5. **俊敏性**
- **俊敏性**：**思いついたアイデアをすぐ形にできること。**
  - オンプレミスだと調達や納品があり、数週間から数ヶ月かかることがある。
6. 従量制の料金体系
- **従量課金モデル：利用した時間に応じて課金される。**
  - サーバー性能、台数、ストレージ容量など
  - オンプレだと自社の資産にはなるが、使わなくなった時に簡単には捨てられない。
7. **スケーラビリティ**
- **スケーラビリティ：拡張可能性。**
  - **ビジネスの成長**に合わせて、サーバーの性能やストレージの容量を増やすことができる。
  - サービス例：Amazon Connect（コールセンターサービス）
8. 世界展開
- **リージョン**：データセンターの集積された拠点。
  - 33箇所（2024年4月現在）
  - 日本国内には東京と大阪
9. 規模の経済
- **規模の経済（economic of scale）：規模が拡大することで単位当たりのコストが軽減される。**
10. ビジネス面の利点
- エンジニアが本来の作業に集中できる
  - 物理的なインフラストラクチャの運用・管理から解放される
- 小さく始めて大きく育てる
  - クラウドの俊敏性を活かすことでビジネスチャンスを逃さない。
- 信頼性の向上
  - 運用の自動化により、システムの信頼性が向上し、高品質なサービスを提供できるようになる。
  - **障害に対して予測、検出、対応を自動化する仕組みを構築できる。**
11. 総所有コスト（TCO）
- オンプレミスのコスト
  - 導入時の人件費の初期コスト
  - 運用に関わるエンジニアの人件費
- クラウドのコスト
  - 初期コストはない
  - ランニングコストは使用したITリソースの**量と時間**
- 単純に初期コストやランニングコストでこれら2つを比較することはできない。 -> そこでTCOの考え方が有効。
- **TCO（Total Cost of Ownership）：サービスの購入（サービスの利用契約）から廃棄（サービスの解約）までにかかる費用の総額。ある程度長い期間でみる。**
12. クラウドにおけるコスト削減の考え方
- オンプレミスからAmazon EC2への移行
- マネージドデータベースサービスの利用
  - Amazon RDSなどを利用することで、バックアップの取得やOS、ミドルウェアのアップデート、可用性の維持から解放される。
- サーバーレスコンピューティングの利用
  - 自分たちでサーバーを構築、管理・運用しなくて良い。
  - (復習)サーバーレス：利用者がサーバーを構築、管理・運用しなくて良いこと。サーバーがないことではない。

### 2026-9-29
1. クラウドアーキテクチャの設計原則
- **Design for failure**：**障害は起きるものとしてシステム設計を行う。**
  - 障害を未然に防止することは難しい
2. Design for failureの設計
  - **単一障害点（Single Point Of Failure）の排除**：アプリケーションサーバーやデータベースサーバーを2台以上用意して可用性を維持する。
    - 例：データベースサーバを2台用意し、常に同期させ、1台に障害が起きてもシステムは止まらない。
  - **様々な角度からの監視**：障害を早く検知できるようにするために**監視（モニタリング）**が必要。
    - CPU、メモリの使用量、ディスクの空き容量
    - **Amazon ClaudWatch**
      - 機能①：利用者（管理者）へのアラート
      - 機能②：サーバーの再起動
      - 機能③：アプリケーションログの出力
  - **復旧手順の自動化**
    - 手動ではなく自動でサーバーを再起動する
    - 応答のない地域とは別の地域に通信を振り分ける
  - **継続的な予行演習**
    - 障害発生時を想定した予行演習の環境を構築
      - 実際に障害を発生させてその影響範囲を観測したり、復旧手順を確認できたりする。
  - **過度なSLAを設定しない**
    - **SLA（Service Level Agreement）**：**構築した製品やサービスを第三者に提供する時に締結する、事業者がユーザに対して一定レベルのサービス品質を保証する契約。**
      - このSLAの契約違反を起こすと違約金や損害賠償が発生する可能性がある。
    - **自社の製品にクラウドが使用されていた場合、クラウドサービスで設定されているSLAよりも厳しい条件のSLAをユーザ間で締結してはいけない。**
  - **伸縮性とスケーラビリティの実現**
    - 障害が検知されたら移動的にサーバーを復旧
    - アクセス数の急増を事前に検知することでサーバーの台数を一時的に増やす
3. 密結合と疎結合
- **密結合：2つ以上の要素がお互いに強く結びついている状態。**
  - メリット：構造が複雑にならず、高速に動作させやすい。
  - デメリット：**部分的な変更がしづらいことや、結合先が利用できない状態の時は自分自身も利用できなくなる。**
- **疎結合：2つ以上の要素が互いに依存せず、独立している状態。**
  - メリット：**部分的な交換や変更がしやすい。結合先が利用できない状態でも自分自身は影響を受けにくい。**
  - デメリット：構造が複雑になりやすく、動作に遅延が生じる場合がある。 
4. マイクロサービスアーキテクチャ
  - マイクロサービスアーキテクチャ：各サービスを疎結合にしたシステム
    - **1つのマイクロサービスの障害によってシステム全体を止めない。**
    - **1つのマイクロサービスが独自にスケーリングできるので、インフラのコストを最適化しやすい。**
    - **障害発生時に部分的にマイクロサービスを切り替えて復旧を行うことができる。**
5. 同期処理と非同期処理
- **同期処理：相手の処理を待つ必要がある。**
- **非同期処理：相手の処理結果を待たずに自分自身の処理を終わらせることができる。**
6. 並行処理と逐次処理
- **並行処理：複数のサーバーを利用して処理を同時に行う。**
  - **全体のパフォーマンスを向上させる処理**のやり方。
  - **耐障害性の向上**を図ることもできる。
- **逐次処理：前の処理結果を次の処理で必要とする場合に有効。**
7. Well-Architected フレームワーク
- **Well-Architectedフレームワーク：AWSクラウド特有の概念や設計原則の指標となる資料。**
  - 目的：要件に合わせて実現できることと、できないことを把握し、実現していくための資料。
    - 100点を取る目的ではない。
- 6つの柱
  - **オペレーションエクセレンスの柱（運用上の優秀性の柱）**
    - 運用自動化
    - プロセスと手順の継続的な改善
  - **セキュリティの柱**
    - データの機密性
    - 完全性
    - 可用性
    - ユーザ管理
    - アクセス権限
  - **パフォーマンス効率の柱**
    - リソースの最適化
    - パフォーマンスのモニタリング
  - **コスト最適化の柱**
    - 不要なコスト回避
  - **持続可能性の柱**
    - 実行中のシステムが環境に対して与える影響を最小限にする
- **AWS Well-Architected Tool**：Well-Architected フレームワークで提唱されているベストプラクティスについて出来ているもの、不要なものをレビューしながら結果をまとめることができる。
- **AWS 規範ガイダンス：AWS Well-Architectedフレームワークに沿ったアーキテクチャ設計を手助けする**リソース。
  - ビジネス目標を達成する具体的な設計パターンやガイドラインを公開している。
8. クラウドへの移行
- 既存のシステムからAWSへ移行するときには、きちんとした**移行計画**が必要。
- クラウド移行の利点
  - その①：俊敏性と柔軟性の向上
    - (復習)俊敏性：ビジネスアイデアをすぐに実現できる
  - その②：固定費用の削減
    - **データセンターやハードウェアの保守が不要**になる。
  - その③：運用負担の削減
    - ハードウェアに加えて、**マネージドサービスを利用することで、OSやミドルウェアの保守作業からも解放される。**
  - その④：セキュリティ向上と信頼性の向上
    - セキュリティやデータ保護などの規則が統制しやすい。 -> コンプライアンス（法令遵守）の体制を組織として確立することができる。
9. クラウド導入フレームワーク（CAF）
- **クラウド導入フレームワーク（AWS Cloud Adoption Framework）：ステークホルダーごとに異なる移行の進め方のベストプラクティスを6視点でまとめた資料。**
  - その①：**ビジネスのパースペクティブ**
    - 視点：**クラウドへの移行、投資の目的やゴールについて考える**
    - 対象：最高経営責任者（CEO）、最高財務責任者（CFO）、最高業務責任者（COO）、最高情報責任者（CIO）、最高技術責任者（CTO）
  - その②：人材のパークペクティブ
    - 視点：変化を受け入れる組織や文化を醸成するためのリーダーシップや人材育成。
    - 対象：最高業務責任者（COO）、最高情報責任者（CIO）、最高技術責任者（CTO）
  - その③：ガバナンスのパースペクティブ
    - 視点：組織としてリスクを最小化しながら移行を推進する。
    - 対象：最高業務責任者（COO）、最高情報責任者（CIO）、最高技術責任者（CTO）
  - その④：プラットフォームのパースペクティブ
    - 視点：拡張性のあるクラウドプラットフォームの構築やモダナイズを行う。
    - 対象：最高技術責任者（CTO）、アーキテクト、エンジニア
  - その⑤：セキュリティのパースペクティブ
    - 視点：データやクラウドインフラについて、高い機密性・完全性・可用性を実現する
    - 対象：最高情報セキュリティ責任者（CISO）、内部監査リーダー、セキュリティ担当アーキテクト、エンジニア
  - その⑥：オペレーションのパースペクティブ
    - 視点：ビジネス要求を満たすサービスを提供を実現する。
    - 対象：運用リーダー、サイト信頼性エンジニア（SRE）
- 用語：
  - CEO（Chief Executive Officer）：最高責任者
    - 役割：会社全体の経営方針を決め、最終的な責任を持つトップ
  - CFO（Chief Financial Officer）：最高財務責任者
    - 役割：お金（予算・投資・コスト・資金繰り）の責任者
  - COO（Chief Operation Officer）：最高業務責任者
    - 役割：日々の事業運営（業務）を回す責任者。CEOの方針を現場で実行する
  - CIO（Chief Information Officer）：最高情報責任者
    - 役割：社内のIT活用や情報システムの戦略を担う責任者
    - 社内向けのIT
  - CTO（Chief Technology Officer）：最高技術責任者
    - 役割：技術の方向性（製品・サービスの技術選定や開発）を担う責任者
    - 社外向けのIT
10. クラウド導入フレームワークの利点
  - **ビジネスリスクの軽減**
    - システムの信頼性やパフォーマンス向上、セキュリティの強化を計画することでリスクを軽減
  - **環境、社会、ガバナンスに関するパフォーマンスの向上**
    - 企業の透明性
    - 社会に与えるサステナビリティ
  - **収益の拡大**
    - 伸縮性、機敏性による新製品や新サービスの創出、新しい顧客の開拓、新規市場への参入
  - **業務効率の向上**
    - 運営コスト
    - 時間あたりの生産性の向上
11. 移行戦略
- **7つのR**：AWSの移行手法を7つに分類したもの。
  1. **リロケート（Relocate）**
    - **オンプレミスでVMWareを使用している場合は、そのままAWSへ**移行できる
  2. **リホスト（Rehost）**
    - **OSやアプリケーションをそのままAmazon EC2へ**移行する
    - **「リフト＆シフト」**とも呼ばれる
  3. **リプラットフォーム（Replatform）**
    - **システムアーキテクチャの変更は行わず、OSやミドルウェアを変更、アップグレード**する。
    - **商用OSをオープンソースOSに移行**する
    - **データベースをAmazon RDSへ移行**する
    - **「リフト・ティンガー＆シフト」**とも呼ばれる
  4. **リファクタ（Refactor）**
    - **システムアーキテクチャの再設計を行い、Amazon Lambdaなどを利用したマイクロサービス化**を行う。
  5. **再購入（Repurchase）**
    - **システムを移行せず、SaaSサービスの利用**に切り替える。
  6. **保持（Retain）**
    - オンプレミスで引き続き運用を行う
    - クラウド移行に関して、ライセンスなどの移行できない要因があるときに採用される
  7. **リタイア（Retire）**
    - サーバーやアプリケーションの廃止
    - 他システムへの統廃合
12. 移行をサポートするサービス
- **AWS Application Discovery Service**
  - 概要：オンプレミス環境に存在するサーバーやデータベースなどのリソース情報を検出する。
  - オンプレミス環境にエージェントプログラムを設置することで情報を収集し、クラウド環境へ保存する。
  - 情報はAmazon S3に保存される。
  - AWS Migration Hubで移行計画を作成する対象にできる
- **AWS Application Migration Service**
  - 概要：オンプレミスのサーバーからデータを継続的にコピーしてアプリケーションをAmazon EC2へ移行する。
  - オンプレミスの仮想環境だけではなく、物理サーバーで動作するアプリケーションにも対応している。
- **AWS Migration Hub**
  - 概要：AWSへの移行計画や評価と追跡を行うために様々なサービスと連携し、情報の収集とダッシュボード機能を提供

### 疑問
